# 発話の契約 — 記録・配信キュー・WebSocket

`chatter-agent-speak`（CLI）が発話を確定させ、`chatter-agent-server` がクライアントへ配信する。この文書は**その境界の契約**を定める。クライアント（表示側アプリ `chatter-mascot`）はここだけを見れば実装できる。

> 設計書 `_workspace/chatter-agent-design.md` §5 が元の一次情報だが、[#8](https://github.com/schwarz9791/chatter-agent/issues/8) で配信の形が変わったので、契約はこちらを正とする。

## 全体像

```
CLI ──┬──▶ speech.jsonl        記録。消さずに残す。誰も読まない
      │
      └──▶ speech/<seq>.json   配信キュー。1文1ファイル
                  │
                  ▼
              server ──▶ WebSocket ──▶ マスコット   テキスト。即座に、seq 順に
                  ▲          （同じポート）    │
                  │      ◀── GET /audio/… ─────┤   音声。必要になったときに取りに行く
                  │      ──▶ WAV ──────────────┤
                  │                            │
                  └────── ack ─────────────────┘
```

**記録と配信を分けてある。** 1つのファイルに兼ねさせると、ローテートを跨ぐ差分読み取りが必要になり、読み手だけが際限なく複雑になる（実際に取りこぼしと二重配信を両方踏んだ）。分ければ、順序はファイル名で決まり、消費は削除で表せる。

**テキストの配信と音声の受け渡しも分けてある**（[#29](https://github.com/schwarz9791/chatter-agent/issues/29)）。テキストは今までどおり WebSocket で即座に流れ、音声は**クライアントが必要になったときに HTTP で取りに行く**。合成はその GET が来たときに走る。

| | |
|---|---|
| **クライアントに合成エンジンが要らない** | XR グラス（Android）には AivisSpeech を置けない。これが分離の動機 |
| **誰も繋いでいない間は合成しない** | 誰も GET しないから。サーバー側に判定コードが無い |
| **同じ文の合成は1回だけ** | サーバーが `(epoch, seq)` で同時要求をまとめる |
| **エンジンが落ちてもテキストは流れる** | 音声だけが 503 になる。「無音の原因」がクライアント側に届く |
| **音声を無視するクライアントも許す** | 字幕や表情だけを使う実装は `audio` を見なければよい。申告は要らない |

## `SpeechRecord` — 記録・キュー・WebSocket で同一

```json
{
  "epoch": "1f0a9c3e-5b62-4f1d-9a77-0e2c8d4b6a31",
  "seq": 1,
  "ts": "2026-08-15T00:12:34.567Z",
  "source": "claude-code",
  "sessionId": "039211d9-…",
  "turnId": "4ccbf3aa-…",
  "messageId": "a94cd2c5-…",
  "kind": "assistant",
  "text": "ログの解析が終わりました。",
  "emotion": "happy"
}
```

| フィールド | 意味 |
|---|---|
| `epoch` | **採番の世代。** `seq` はこの中でしか一意でない。採番がやり直されると別の値になる（下の「採番のやり直し」） |
| `seq` | 単一ワーカーがロック下で採番する 1 始まりの整数。**キューのファイル名と ack のキーを兼ねる。`epoch` を跨いで一意ではない** |
| `ts` | ISO8601 |
| `source` | `claude-code`。将来 別のプロデューサーが同じ形で書ける余地 |
| `sessionId` / `turnId` / `messageId` | 絞り込みとグルーピング。取れないときは `null` |
| `kind` | `assistant`（通常の発言）/ `prompt`（応答待ち通知）。**未知の `kind` は `assistant` として扱うこと** |
| `text` | **1文。** Markdown 除去済み |
| `emotion` | `neutral` / `happy` / `angry` / `sad` / `relaxed` / `surprised`。VRM の標準 expression 名と一対一 |

**1文1行 / 1文1ファイル。** 記録とキューはこの形で完全に同じ。

★ **配信フレームだけは `audio` が1つ多い**（下の「WebSocket」）。CLI が書く時点では音声が
存在しないので、記録にもキューにも載せられない。**フレームを保存して記録と突き合わせるときは
`audio` を落とすこと。**

## 採番のやり直し — `epoch`

**ランタイムルート（または `speech.state.json` と `speech.jsonl` の両方）が消えると、CLI の採番は 1 に戻る。**
`seq` だけを覚えているクライアントは、そこで「もう喋った」と誤判定して**何百文でも一切喋らなくなる**（エラーも出ない）。

`epoch` はこのやり直しを表す。**やり直しと一対一**で、採番が続くなら同じ値のまま、やり直されたら別の値になる。

| | |
|---|---|
| 誰が決めるか | **CLI**（採番と同じ場所）。`speech.state.json` に持つ |
| 形 | 不透明な文字列。`[A-Za-z0-9][A-Za-z0-9._-]{0,63}` に収まる。**中身を解釈しないこと** |
| 比較 | **等値だけ。** 順序は無い（「新しい epoch」を値から判定できない） |
| 1メッセージの中 | `seq` / `messageId` / `ts` と同じく**同値** |

**キューには常に1つの世代しか無い。** 採番がやり直されたとき、旧世代の entry を捨てるのは
ロックを持っている書き手（CLI）で、最初の `enqueue` の**前**に配信キューを空にする。
サーバー側では「どちらの世代が新しいか」を判定できない — やり直し直後のキューは
`1(新) 2(新) … 400(旧)` になり、ファイル名の昇順では**新しい世代が先頭に来る**。

> サーバーには安全網だけある。**present な entry のうち `ts` が最も新しい世代**を配信し、
> それ以外の世代の entry は配信しない。CLI を経由しない経路（バックアップの復元、
> 手で置いたファイル）のためのもので、通常は発火しない。
>
> ★ **サーバーは世代違いの entry を削除しない。** 「消す」の分担（下の表）は変わらない。
> 時計が巻き戻ると新旧の判定が逆転しうるし、CLI とサーバーは別のロックなので、
> 全件を読んでから消す間に CLI が書いた entry を巻き込む。配信しないだけに留め、
> 掃除は CLI の後始末（採番がやり直されたら、最初の publish の前にキューを空にする）と
> サーバー起動時の掃除に任せる。
>
> ★ 配信済みの記憶は `seq` で持つので、**`clear()` の直後に同じ `seq` が別世代の内容で
> 書き直されたこと**はファイル名の集合からは見えない。サーバーは毎回キューの先頭を
> 1件だけ読んで世代を確かめる。

## 発話の粒度 — 1メッセージ分がまとまって届く

**アシスタントの発言は、メッセージが閉じた（`final:true`）ときに全文まとめて確定する。** CLI は `final` が来るまで1文も出さない（[#30](https://github.com/schwarz9791/chatter-agent/issues/30)）。

その結果、`kind: "assistant"` の発話には次の保証が付く。

| | |
|---|---|
| `seq` | **1メッセージ分が連続する。** 間に他メッセージの発話が挟まらない |
| `messageId` | **その連続の中で同一** |
| `ts` | **その連続の中で同値** |

単一ワーカーがロック下で1回だけ `append` し、`ts` は `append` ごとに1回だけ計算されるため、上の3つの保証（`seq` の連続性・`messageId` の同一性・`ts` の同値性）は成立する。

**ただし、これは「バッチの中身が壊れない」保証であって「クライアントが `messageId` でバッチをまとめてよい」保証ではない。** 次の3点により、`messageId` の変化だけを根拠にした安全なバッチ化はできない。

1. **バッチの終端マーカーがワイヤ上に無い。** `messageId` が変わるのは次のメッセージの発話が届いたときで、それは数十秒後になりうる（`AskUserQuestion` の直前など）。「このバッチはもう続きが無い」と確定する手段がクライアント側に無い
2. **`seq` に欠番が出たバッチでは連続性判定が成立しない。** 上限超過やサーバー再起動時の切り詰め（下の「起動時に古い entry だけを捨てる」）で `seq` は飛びうる（下の「クライアント側の責務」3）。同じ `messageId` のはずの発話の一部だけが欠けても、クライアント側にそれを検出する情報が無い
3. **救済経路（`final` を待たずに打ち切って publish するパス）のバッチも、見た目は同じ `kind: "assistant"` で届く。** 通常どおりメッセージが閉じて publish されたのか、救済経路で途中から打ち切られたのかを示す情報がワイヤ上に無いので、「`messageId` が変わったから前のバッチは完全だった」という前提も成立しない

> `kind: "prompt"`（応答待ち通知）はメッセージではなく1イベント単位。上の保証はアシスタントの発言についてのもの。

これを踏まえて、クライアント側で2つ注意する。

1. **★ `ts` を単独のキーにしないこと。** 同一メッセージ内で同値になるので、`ts` だけで Map を引いたり重複排除したりすると**1メッセージが1文に潰れる**。重複排除は `(epoch, seq)` の組で行う（下の「クライアント側の責務」1）
2. **★ 数十秒の無音は正常。** `final` はメッセージが閉じる瞬間＝次のブロックが始まるときに届き、`AskUserQuestion` の直前では数十秒に達する。その間サーバーは1フレームも送らない。**「接続が死んだ」と誤判定しないこと** — 生存確認はサーバーの ping（30秒間隔）で行う（下の「参照実装」の最終項）

## 配信キュー — `{root}/speech/`

```
{root}/speech/000000000123.json    ← ファイル名が seq（12桁ゼロ埋め）
{root}/speech/000000000124.json
```

| | |
|---|---|
| 書く | CLI（ロック下）。**tmp + rename** で置くので、server が書きかけを読むことはない |
| 読む | server が 50ms ごとに `readdir`。ファイル名から `seq` を読んで昇順に配信する |
| 消す | **上限超過は CLI**（書いた直後に切る）。**ack を受けたぶんと起動時の掃除は server** |

ファイル監視は使わない。単一ファイルの監視でローテートの取りこぼしを実測で踏んでおり、`readdir` の方が経路として単純で確実。キューは高々数百件なので、20回/秒でも誤差。

**サーバーは同時に1台だけ動く。** bind の前に `{root}/server.lock` を取り、2台目は起動に失敗する。配信キューはこのルート直下に1つしかないため、2台が同時に読み書きすると起動時の掃除や ack の削除が競合する。

## WebSocket

`ws://<host>:<port>`。既定は `0.0.0.0:8570`。テキストフレームのみ。

### サーバー → クライアント

`SpeechRecord` に `audio` を足した JSON（`SpeechFrame`）を1行1フレームで送る。**それ以外は送らない。**

```json
{ "epoch": "1f0a9c3e-…", "seq": 42, "…": "…",
  "audio": { "path": "/audio/1f0a9c3e-…-000000000042.wav", "format": "wav" } }
```

| | |
|---|---|
| `audio.path` | **相対パス。** クライアントが**自分の接続先の authority に対して解決する**（`ws://host:port` → `http://host:port`）。★ サーバーは自分がどのアドレスで到達されたかを知らない（既定の bind は `0.0.0.0` で、これは接続先ではない）。絶対 URL を期待しないこと |
| `audio.format` | 今は `"wav"` だけ。**知らない値は「音声なし」として扱うこと** |
| `audio: null` | 音声は用意されない（`ttsEnabled: false`、または読み上げる中身が無い文）。**何も鳴らさずに ack する** |

- 接続すると、**配信済みでまだ ack していない発話**が届く（`?since=` は廃止した）。まだ配信していない分（server がまだ poll していない、または未読の entry）は含まれない
- ★ **接続の前に message ハンドラを張ること。** 接続直後の追いつきは同期で流れるので、`open` を待ってから張ると取りこぼす
- 配信が詰まる（クライアントが遅い）と、**フレームを捨てるのではなく接続を切る**（1013）。繋ぎっぱなしで1文だけ欠けるより、切って繋ぎ直させる方が事故に気づける

### 音声 — `GET /audio/<epoch>-<seq>.wav`

**WebSocket と同じポート。** フレームの `audio.path` をそのまま使う。

| | |
|---|---|
| `200` | WAV が返る。**サーバーは合成が終わるまでレスポンスを保留する**（下の「応答の期限」まで） |
| `503` | **あとで取りに来い。** エンジンに繋がらない・合成が返らない・まだ終わっていない。`Retry-After`（秒）を返す。★ **試行回数に数えないこと**（下の「クライアント側の責務」8） |
| `404` | **永久に用意できない。** キューから消えた（ack / 上限超過 / 起動時の掃除）、世代違いの古い URL、読み上げる中身が無い文、`ttsEnabled: false`。`audio: null` と同じ扱いで、warn して ack する |
| `403` | `Origin` が `allowedOrigins` に無い（WebSocket と同じ規則） |
| `405` | `GET` / `HEAD` / `OPTIONS` 以外。`Allow` を返す |

`OPTIONS`（プリフライト）は `204` + `Allow` / `Access-Control-Allow-Methods`。
**`Access-Control-Allow-Headers` に `range` は入れない** — 下のとおり Range は実装しないので、
入れると「対応していないものを対応している」と言うことになる。

- ★ **`Retry-After` は CORS の safelist に入っていない。** サーバーは
  `Access-Control-Expose-Headers: retry-after` を返す。返さないと、**ブラウザ / WebView の JS
  からはこのヘッダが読めない**（#29 が主目的にしている XR / Unity WebGL / Electron renderer）
- ★ **合成のエラーを `404` に落とさないこと。** 「エンジンが 4xx を返したなら恒久的だから
  諦めさせる」は一見筋が通るが、`404` はクライアント側で ack まで通り、**キューの本文が
  物理削除される**。`ttsSpeakerId` を30秒後に直しても復元できない（`503` のままなら直した瞬間に
  全部鳴る）。しかも「恒久」の線引きは実質不可能で、モデルロード中の 4xx・`ttsBaseUrl` の
  パス違いで別サービスが返す 404/405・プロキシの 407 まで巻き込む

- **`Range` は実装しない。** `Accept-Ranges: none` を返して常に全体を送る。1文ぶんの WAV は
  数百KB なので、分割で得るものが無い（Unity の `UnityWebRequestMultimedia` や ExoPlayer は
  `Range` を投げてくるが、無視して 200 に全体を返すのは仕様上正しい）
- **音声はローカルに落としてから再生すること。** URL から直接ストリーム再生すると、
  ack でキューが消えた瞬間に途中で切れる
- 合成した WAV は**サーバーのプロセス内**にしか無い。上限（件数とバイト数）で溢れたら捨てられ、
  次の GET で作り直される。**取り直せば同じものが返る**前提で書いてよい
- **同時に走らせる合成には上限がある。** 超えた分は `503`。この口は既定で `0.0.0.0` に無認証で
  開いており、`/synthesis` は CPU 律速なので、上限が無いとキューぶんの GET を並べるだけで
  実質 DoS になる

#### 応答の期限

**サーバーは `GET` の応答を `synthesisTimeoutMs` で打ち切り、`503` を返す。合成は止めない。**

走らせたままにしておけば、終わった時点でサーバー内のキャッシュに入り、**クライアントの
取り直しが即 `200` になる**。打ち切るのは応答だけで、合成そのものを短く切ると
モデルロード中の1文目が永久に完成しない。

> ★ この期限があるので、**「クライアントの取得タイムアウトはサーバーの合成タイムアウトより
> 長くしなければならない」という設定間の暗黙の順序制約は無い。** 守られなかったときの症状は
> 「試行回数を消費して発話が捨てられる」で、設定からは読み取れないたぐいのものだった。

### クライアント → サーバー

**ack だけ。**

```json
{ "type": "spoken", "seq": 42, "epoch": "1f0a9c3e-…" }
```

**累積 ack**（「seq 42 まで喋り終えた」）。1つ落ちても次で自己修復する。サーバーは `seq <= 42` のキューを消す。

`epoch` は**任意フィールド**。省略（または JSON の `null`）は「世代を名乗らない ack」として現在の世代のものに扱われる。
**載せることを強く推奨する** — 採番がやり直された直後に旧世代の ack が届くと、`ackUpTo` は
`seq <= N` を**ファイル名で範囲削除**するので、**まだ喋っていない新しい entry がまとめて消える**。
`epoch` が載っていれば、サーバーがその ack を弾いて警告を出す。

`type` が `"spoken"` でない、`seq` が**非負の安全整数**でない、`epoch` が載っているのに形が違う、
JSON として読めない ── これらは**メッセージとしては届いたが捨てられる**（接続は切れない。
サーバーは接続ごとに1回だけ警告を出す）。

> ★ **`epoch: null` は「省略」と同じ扱いで、捨てられない。** 未設定の optional を明示的な
> `null` にするのは Unity の `JsonUtility`、多くの C# シリアライザ、Go の `encoding/json`
> （ポインタ）、Python の `json.dumps(None)` の既定なので、ここで弾くと
> **契約どおりのつもりのクライアントの ack がすべて消える**。

これとは別に、**フレームそのものが 4KB を超えると黙って捨てられるのではなく、接続が 1009 で切られる。** 上の「黙って捨てられる」は正常なサイズの読めないメッセージの話で、上限超過は message イベント自体が発火せず接続断に直結する、別の失敗モード。この上限は受信専用で、サーバーからの送信（`SpeechRecord` の配信）には効かない。

## ack はフロー制御であって、耐久性の保証ではない

TTS + 再生は生成よりずっと遅い。Claude Code は 2 秒で 20 文吐くが、マスコットは 60 秒かけて喋る。**キューは実質バッファで、ack は「1文喋り終わった、次をくれ」という credit。**

この読み方から、次の3つが同じ原則で説明できる。

| | |
|---|---|
| **サーバーは起動時に、古い entry だけを捨てる** | 全消しにはしない。[#30](https://github.com/schwarz9791/chatter-agent/issues/30) で発話がメッセージ単位（1メッセージ = 1回の enqueue）になったため、この境界は「メッセージを丸ごと残すか丸ごと捨てるか」の二択にしかならない——段落の途中から喋り出す事故はもう起きない。境界より新しく enqueue されたメッセージは丸ごと届き、古ければ丸ごと消える（例: 再起動の11秒前に enqueue された30文のメッセージは、既定の `STARTUP_KEEP_MS = 10_000` では丸ごと消え、クライアントには1文も届かない）。10 秒以上前に止まっていた発話を今さら読ませたくない、という方針で選んだ値で、消えること自体は許容している |
| **上限を超えたら古い方から捨てる（CLI が切る）** | クライアントが繋がっていなければ ack は来ない。サーバーが落ちていても ack は来ないので、歯止めをかけられるのは書き手（CLI）だけ。時間ベースの GC を足すより、上限で溢れさせる方が判断基準が1本で済む |
| **複数クライアントでは、どれか1つの ack で消してよい** | 内容は既にソケットへ配信済みで、ファイルはキュー entry でしかない |

## クライアント側の責務

1. **`(epoch, seq)` の組で重複排除すること。** 再接続すると未 ack 分が再送される。同じ組を2度受け取ったら後を捨てる。**`seq` 単独では足りない**（上の「採番のやり直し」）。★ **`ts` を混ぜないこと** — 同一メッセージ内で同値になるので、キーに含めても世代の区別にはならない
2. **喋り終えたら ack すること。** ack しないとキューが上限まで溜まり、古い方から捨てられる
3. **`seq` の飛びは欠落。** 上限超過、またはサーバーの再起動（起動時に古い entry を捨てる）で起きうる。埋める手段は無いので、そのまま進む
4. **未知の `kind` は `assistant` として扱う**
5. **切断されたら繋ぎ直すこと。** バックプレッシャによる切断（1013）も含め、繋ぎ直せば未 ack 分が接続直後の追いつきで再送される
6. **同じルートに対して繋ぐクライアントは1台にすること。** ack は累積で、サーバーは `seq <= N` を**キューから物理削除**する。誰が受け取ったかは見ない。速いクライアントの ack が、遅いクライアントのまだ喋っていない entry を消す（音声も 404 になる）
7. **`epoch` が変わったら、覚えていることを全部捨てること。** 重複排除の記憶、取得中・再生待ちの item、溜めている ack。**旧世代の ack を送らないこと**（上の「クライアント → サーバー」）
8. **★ `503` を「失敗」に数えないこと。** 音声の取得に上限回数を設けるのは正しいが、`503` でそれを消費すると、**サーバー側のエンジンを起動し忘れているだけで、溜まっていた発話が数百 ms で全部 ack されて消える**。`503` は待って取り直し、`404` と転送エラーだけを回数に数える。用意できない状態が続いたら、**設定を疑う手がかりをログに出すこと** — 合成がサーバーへ移った結果、`ttsBaseUrl` / `ttsSpeakerId` の間違いもエンジンの不在も、クライアントからは「無音」としてしか見えない

### 参照実装

**`core/src/player/` が上の8つを全部踏んでいる**（`chatter-agent-player`）。クライアントを書くときの突き合わせ先として使える。実装で踏んだ落とし穴のうち、契約から読み取りにくいもの:

- **`epoch` は「検出」を不要にするだけで、「取り扱い」までは消さない。** 非同期の結果・一時ファイル名・
  保留 ack は依然として `(世代, seq)` で識別する必要がある。`seq` をキーにした Map / ファイル名は、
  やり直しを跨いだ瞬間に別の文と衝突する（古い合成結果が新しい文の音声として採用される、
  再生中の一時ファイルが上書きされる、など）。
  ★ **サーバーの `epoch` をそのままファイル名に入れないこと。** 外部由来の文字列なので、
  内部で連番に読み替えてから使う（`player/playbackQueue.ts` の `state.epoch` がそれ）
- **ack を単調増加に縛らない。** 縛ると採番やり直しの後に ack が一切送られず、キューが上限まで溜まって古い方から捨てられ続ける。逆に、採番がやり直された後に**古い ack を送ってはいけない**（まだ喋っていない新しい entry が消える）
- **再接続の `open` では保留していた ack を送らないこと。** WebSocket は必ず `open` → `message` の
  順に発火するので、`open` の時点では**相手が同じサーバーか判断できない**（`epoch` が載るのは
  フレームで、ハンドシェイクではない）。最初のフレームを受けて世代が続いていると確認できてから送る。
  先に送ると、作り直されたサーバーの配信済み・未発話の entry がまとめて消える
- **消費済みの記憶が溢れても、採番のやり直しと取り違えないこと。** 記憶の上限はサーバー側の
  キュー上限とズレうる。溢れた再送を「やり直し」と読むと状態を捨てて**同じ文を2回喋る**。
  `epoch` が同じなら溢れ、違えばやり直し、と分けられる
- **失敗した発話も「喋り終えた」と同じ経路で ack する。** 音声を取れなかった文をその場で ack すると、先読みしているぶんだけ手前の未再生 entry を巻き込んで消す
- **接続の前に message ハンドラを張る**（上の★）
- **サーバーの ping が途切れたことを検出する。** サーバーは 30 秒ごとに ping を打って無応答の接続を切るが、**その対称の仕組みはクライアント側にしか置けない**。スリープ復帰や NAT テーブル切れで half-open になると、クライアントは「接続中」のまま永久に無音になる
- **音声の GET にもタイムアウトを置く。** 返らない相手を掴むと head-of-line blocking で**以後すべてが無音になり、エラーも1行も出ない**。★ **サーバー側の設定と突き合わせる必要は無い** — サーバーが応答を `synthesisTimeoutMs` で打ち切って `503` を返す（上の「応答の期限」）ので、待たされ続ける側は塞がっている
- **`503` が続いたら、取り直す間隔を伸ばすこと。** 固定間隔だと、エンジンを起動し忘れているだけで **1 req/s のループが恒久的に回る**。指数バックオフにして上限で頭を打たせ、`200` が返ったら元に戻す

## セキュリティ

**`Origin` ヘッダを持つ接続は、`allowedOrigins` に載っていなければ拒否する。** WebSocket は CORS の対象外なので、これが無いとユーザーが開いた任意の Web ページが `new WebSocket("ws://127.0.0.1:8570")` で会話を読み、ack を投げてマスコットを黙らせられる。`host` を `127.0.0.1` に絞っても塞がらない。

**`GET /audio/…` にも同じ規則を適用する。** そのうえで、**許可した `Origin` には `Access-Control-Allow-Origin` を返す** — WebSocket と違って `fetch` は CORS の対象なので、403 を返さないだけでは足りず、許可していてもブラウザ側で音声だけブロックされる。

> ★ **ブラウザの `<audio src>` は `Origin` を送らないので、この検査を素通りする**（読み取りはできないが再生はできる）。実質的な防御は **`epoch` が推測しにくいこと**になっている。`epoch` を短縮したり、連番のような予測可能な値に変えたりしないこと。

`allowedOrigins` の既定は `[]`（＝ `Origin` 付きの接続は全拒否）。**完全一致のみで、前方一致やワイルドカードは無い。**

**`Origin` が付くかどうかは、クライアントの実装言語ではなく「WebView / ブラウザから張るか」で決まる。**

| 繋ぎ方 | `Origin` | 対応 |
|---|---|---|
| ネイティブ側から張る（Unity、Electron の main プロセス、Tauri の Rust、Wails の Go など） | 付かない | 設定不要 |
| WebView / ブラウザから張る（Tauri の `tauri://localhost`、Electron の renderer、Unity の WebGL ビルドなど） | 付く | 実際のオリジンを `allowedOrigins` に足す |

`tauri://localhost` のような**ブラウザからは名乗れないスキーム**を足すぶんには、上の脅威（任意の Web ページが繋ぐ）は塞がったまま。`http://localhost:*` を足すときは、そのポートを開発サーバー以外に使わないこと。

**LAN 上の他端末に対する認証は無い。** 既定の `0.0.0.0` バインドは、同一 LAN の誰でもエージェントの発言を読める状態を意味する。**会話のテキストに加えて、合成した音声も同じ口から取れる。** 信頼できないネットワークでは `host` を `127.0.0.1` にすること。認証の追加は [#3](https://github.com/schwarz9791/chatter-agent/issues/3)。

## 記録 — `{root}/speech.jsonl`

配信とは独立した、消さない記録。**誰も tail しない**ので、ローテートの正しさは要求されない。上限（既定 5MB）を超えたら `speech.1.jsonl` に退避するだけで、前の退避は上書きされる。

`seq` の採番は `speech.state.json`（`{nextSeq, epoch}`）に持ち、記録の末尾からも復旧できる
（`seq` は両者がずれたら大きい方を採る。`epoch` は state → 記録の末尾行の順に拾い、
**`seq` と同じ行から採る**）。どちらからも `epoch` が読めず、しかも `seq` は復旧できたときは
`"legacy"` を採る — ここで新しい値を作ると、この機能より前のデータを持つユーザーが
アップグレードした瞬間に「採番がやり直された」と読まれ、キューが捨てられる。
