# 発話の契約 — 記録・配信キュー・WebSocket

`chatter-agent-speak`（CLI）が発話を確定させ、`chatter-agent-server` がクライアントへ配信する。この文書は**その境界の契約**を定める。クライアント（表示側アプリ `chatter-mascot`）はここだけを見れば実装できる。

> 設計書 `_workspace/chatter-agent-design.md` §5 が元の一次情報だが、[#8](https://github.com/schwarz9791/chatter-agent/issues/8) で配信の形が変わったので、契約はこちらを正とする。

## 全体像

```
CLI ──┬──▶ speech.jsonl        記録。消さずに残す。誰も読まない
      │
      └──▶ speech/<seq>.json   配信キュー。1文1ファイル
                  │
                  ▼
              server ──▶ WebSocket ──▶ マスコット
                  ▲                        │
                  └────── ack ─────────────┘
```

**記録と配信を分けてある。** 1つのファイルに兼ねさせると、ローテートを跨ぐ差分読み取りが必要になり、読み手だけが際限なく複雑になる（実際に取りこぼしと二重配信を両方踏んだ）。分ければ、順序はファイル名で決まり、消費は削除で表せる。

## `SpeechRecord` — 記録・キュー・WebSocket で同一

```json
{
  "seq": 1,
  "ts": "2026-08-15T00:12:34.567Z",
  "source": "claude-code",
  "sessionId": "039211d9-…",
  "turnId": "4ccbf3aa-…",
  "messageId": "a94cd2c5-…",
  "kind": "assistant",
  "text": "ログの解析が終わりました。",
  "emotion": "happy"
}
```

| フィールド | 意味 |
|---|---|
| `seq` | 単一ワーカーがロック下で採番する 1 始まりの整数。**キューのファイル名と ack のキーを兼ねる** |
| `ts` | ISO8601 |
| `source` | `claude-code`。将来 別のプロデューサーが同じ形で書ける余地 |
| `sessionId` / `turnId` / `messageId` | 絞り込みとグルーピング。取れないときは `null` |
| `kind` | `assistant`（通常の発言）/ `prompt`（応答待ち通知）。**未知の `kind` は `assistant` として扱うこと** |
| `text` | **1文。** Markdown 除去済み |
| `emotion` | `neutral` / `happy` / `angry` / `sad` / `relaxed` / `surprised`。VRM の標準 expression 名と一対一 |

**1文1行 / 1文1ファイル / 1文1フレーム。** 3箇所で同じ形なので、変換は要らない。

## 発話の粒度 — 1メッセージ分がまとまって届く

**アシスタントの発言は、メッセージが閉じた（`final:true`）ときに全文まとめて確定する。** CLI は `final` が来るまで1文も出さない（[#30](https://github.com/schwarz9791/chatter-agent/issues/30)）。

その結果、`kind: "assistant"` の発話には次の保証が付く。

| | |
|---|---|
| `seq` | **1メッセージ分が連続する。** 間に他メッセージの発話が挟まらない |
| `messageId` | **その連続の中で同一** |
| `ts` | **その連続の中で同値** |

単一ワーカーがロック下で1回だけ `append` し、`ts` は `append` ごとに1回だけ計算されるため、上の3つの保証（`seq` の連続性・`messageId` の同一性・`ts` の同値性）は成立する。

**ただし、これは「バッチの中身が壊れない」保証であって「クライアントが `messageId` でバッチをまとめてよい」保証ではない。** 次の3点により、`messageId` の変化だけを根拠にした安全なバッチ化はできない。

1. **バッチの終端マーカーがワイヤ上に無い。** `messageId` が変わるのは次のメッセージの発話が届いたときで、それは数十秒後になりうる（`AskUserQuestion` の直前など）。「このバッチはもう続きが無い」と確定する手段がクライアント側に無い
2. **`seq` に欠番が出たバッチでは連続性判定が成立しない。** 上限超過やサーバー再起動時の切り詰め（下の「起動時に古い entry だけを捨てる」）で `seq` は飛びうる（下の「クライアント側の責務」3）。同じ `messageId` のはずの発話の一部だけが欠けても、クライアント側にそれを検出する情報が無い
3. **救済経路（`final` を待たずに打ち切って publish するパス）のバッチも、見た目は同じ `kind: "assistant"` で届く。** 通常どおりメッセージが閉じて publish されたのか、救済経路で途中から打ち切られたのかを示す情報がワイヤ上に無いので、「`messageId` が変わったから前のバッチは完全だった」という前提も成立しない

> `kind: "prompt"`（応答待ち通知）はメッセージではなく1イベント単位。上の保証はアシスタントの発言についてのもの。

これを踏まえて、クライアント側で2つ注意する。

1. **★ `ts` を単独のキーにしないこと。** 同一メッセージ内で同値になるので、`ts` だけで Map を引いたり重複排除したりすると**1メッセージが1文に潰れる**。重複排除は `(seq, ts)` の組で行う（下の「クライアント側の責務」1）
2. **★ 数十秒の無音は正常。** `final` はメッセージが閉じる瞬間＝次のブロックが始まるときに届き、`AskUserQuestion` の直前では数十秒に達する。その間サーバーは1フレームも送らない。**「接続が死んだ」と誤判定しないこと** — 生存確認はサーバーの ping（30秒間隔）で行う（下の「参照実装」の最終項）

## 配信キュー — `{root}/speech/`

```
{root}/speech/000000000123.json    ← ファイル名が seq（12桁ゼロ埋め）
{root}/speech/000000000124.json
```

| | |
|---|---|
| 書く | CLI（ロック下）。**tmp + rename** で置くので、server が書きかけを読むことはない |
| 読む | server が 50ms ごとに `readdir`。ファイル名から `seq` を読んで昇順に配信する |
| 消す | **上限超過は CLI**（書いた直後に切る）。**ack を受けたぶんと起動時の掃除は server** |

ファイル監視は使わない。単一ファイルの監視でローテートの取りこぼしを実測で踏んでおり、`readdir` の方が経路として単純で確実。キューは高々数百件なので、20回/秒でも誤差。

**サーバーは同時に1台だけ動く。** bind の前に `{root}/server.lock` を取り、2台目は起動に失敗する。配信キューはこのルート直下に1つしかないため、2台が同時に読み書きすると起動時の掃除や ack の削除が競合する。

## WebSocket

`ws://<host>:<port>`。既定は `0.0.0.0:8570`。テキストフレームのみ。

### サーバー → クライアント

`SpeechRecord` の JSON を1行1フレームで送る。**それ以外は送らない。**

- 接続すると、**配信済みでまだ ack していない発話**が届く（`?since=` は廃止した）。まだ配信していない分（server がまだ poll していない、または未読の entry）は含まれない
- ★ **接続の前に message ハンドラを張ること。** 接続直後の追いつきは同期で流れるので、`open` を待ってから張ると取りこぼす
- 配信が詰まる（クライアントが遅い）と、**フレームを捨てるのではなく接続を切る**（1013）。繋ぎっぱなしで1文だけ欠けるより、切って繋ぎ直させる方が事故に気づける

### クライアント → サーバー

**ack だけ。**

```json
{ "type": "spoken", "seq": 42 }
```

**累積 ack**（「seq 42 まで喋り終えた」）。1つ落ちても次で自己修復する。サーバーは `seq <= 42` のキューを消す。

`type` が `"spoken"` でない、`seq` が**非負の安全整数**でない、JSON として読めない ── これらは**メッセージとしては届いたが黙って捨てられる**（接続は切れない）。

これとは別に、**フレームそのものが 4KB を超えると黙って捨てられるのではなく、接続が 1009 で切られる。** 上の「黙って捨てられる」は正常なサイズの読めないメッセージの話で、上限超過は message イベント自体が発火せず接続断に直結する、別の失敗モード。この上限は受信専用で、サーバーからの送信（`SpeechRecord` の配信）には効かない。

## ack はフロー制御であって、耐久性の保証ではない

TTS + 再生は生成よりずっと遅い。Claude Code は 2 秒で 20 文吐くが、マスコットは 60 秒かけて喋る。**キューは実質バッファで、ack は「1文喋り終わった、次をくれ」という credit。**

この読み方から、次の3つが同じ原則で説明できる。

| | |
|---|---|
| **サーバーは起動時に、古い entry だけを捨てる** | 全消しにはしない。[#30](https://github.com/schwarz9791/chatter-agent/issues/30) で発話がメッセージ単位（1メッセージ = 1回の enqueue）になったため、この境界は「メッセージを丸ごと残すか丸ごと捨てるか」の二択にしかならない——段落の途中から喋り出す事故はもう起きない。境界より新しく enqueue されたメッセージは丸ごと届き、古ければ丸ごと消える（例: 再起動の11秒前に enqueue された30文のメッセージは、既定の `STARTUP_KEEP_MS = 10_000` では丸ごと消え、クライアントには1文も届かない）。10 秒以上前に止まっていた発話を今さら読ませたくない、という方針で選んだ値で、消えること自体は許容している |
| **上限を超えたら古い方から捨てる（CLI が切る）** | クライアントが繋がっていなければ ack は来ない。サーバーが落ちていても ack は来ないので、歯止めをかけられるのは書き手（CLI）だけ。時間ベースの GC を足すより、上限で溢れさせる方が判断基準が1本で済む |
| **複数クライアントでは、どれか1つの ack で消してよい** | 内容は既にソケットへ配信済みで、ファイルはキュー entry でしかない |

## クライアント側の責務

1. **`seq` と `ts` の組で重複排除すること。** 再接続すると未 ack 分が再送される。同じ `(seq, ts)` を2度受け取ったら後を捨てる。**`seq` 単独では足りない** — ランタイムルートが作り直されると採番が 1 からやり直され、`seq` だけで「もう喋った」を覚えていると**何百文でも一切喋らなくなる**（エラーも出ない）。再送は必ず同じ `ts` を持ち、新しい採番は別の `ts` を持つ
2. **喋り終えたら ack すること。** ack しないとキューが上限まで溜まり、古い方から捨てられる
3. **`seq` の飛びは欠落。** 上限超過、またはサーバーの再起動（起動時に古い entry を捨てる）で起きうる。埋める手段は無いので、そのまま進む
4. **未知の `kind` は `assistant` として扱う**
5. **切断されたら繋ぎ直すこと。** バックプレッシャによる切断（1013）も含め、繋ぎ直せば未 ack 分が接続直後の追いつきで再送される
6. **同じルートに対して繋ぐクライアントは1台にすること。** ack は累積で、サーバーは `seq <= N` を**キューから物理削除**する。誰が受け取ったかは見ない。速いクライアントの ack が、遅いクライアントのまだ喋っていない entry を消す

### 参照実装

**`core/src/player/` が上の6つを全部踏んでいる**（`chatter-agent-player`）。クライアントを書くときの突き合わせ先として使える。実装で踏んだ落とし穴のうち、契約から読み取りにくいもの:

- **採番のやり直しは `(seq, ts)` の1点では終わらない。** クライアント内部で「エポック」を数え、
  **非同期の結果・一時ファイル名・保留 ack のすべてをエポックで識別する**必要がある。`seq` を
  キーにした Map / ファイル名は、やり直しを跨いだ瞬間に別の文と衝突する（古い合成結果が新しい
  文の音声として採用される、再生中の一時ファイルが上書きされる、など）
- **ack を単調増加に縛らない。** 縛ると採番やり直しの後に ack が一切送られず、キューが上限まで溜まって古い方から捨てられ続ける。逆に、採番がやり直された後に**古い ack を送ってはいけない**（まだ喋っていない新しい entry が消える）
- **再接続の `open` では保留していた ack を送らないこと。** WebSocket は必ず `open` → `message` の
  順に発火するので、`open` の時点では**相手が同じサーバーか判断できない**。最初のフレームを受けて
  採番が続いていると確認できてから送る。先に送ると、作り直されたサーバーの配信済み・未発話の
  entry がまとめて消える
- **消費済みの記憶が溢れても、採番のやり直しと取り違えないこと。** 記憶の上限はサーバー側の
  キュー上限とズレうる。溢れた再送を「やり直し」と読むと状態を捨てて**同じ文を2回喋る**
- **失敗した発話も「喋り終えた」と同じ経路で ack する。** 合成に失敗した文をその場で ack すると、先読みしているぶんだけ手前の未再生 entry を巻き込んで消す
- **接続の前に message ハンドラを張る**（上の★）
- **サーバーの ping が途切れたことを検出する。** サーバーは 30 秒ごとに ping を打って無応答の接続を切るが、**その対称の仕組みはクライアント側にしか置けない**。スリープ復帰や NAT テーブル切れで half-open になると、クライアントは「接続中」のまま永久に無音になる

## セキュリティ

**`Origin` ヘッダを持つ接続は、`allowedOrigins` に載っていなければ拒否する。** WebSocket は CORS の対象外なので、これが無いとユーザーが開いた任意の Web ページが `new WebSocket("ws://127.0.0.1:8570")` で会話を読み、ack を投げてマスコットを黙らせられる。`host` を `127.0.0.1` に絞っても塞がらない。

`allowedOrigins` の既定は `[]`（＝ `Origin` 付きの接続は全拒否）。**完全一致のみで、前方一致やワイルドカードは無い。**

**`Origin` が付くかどうかは、クライアントの実装言語ではなく「WebView / ブラウザから張るか」で決まる。**

| 繋ぎ方 | `Origin` | 対応 |
|---|---|---|
| ネイティブ側から張る（Unity、Electron の main プロセス、Tauri の Rust、Wails の Go など） | 付かない | 設定不要 |
| WebView / ブラウザから張る（Tauri の `tauri://localhost`、Electron の renderer、Unity の WebGL ビルドなど） | 付く | 実際のオリジンを `allowedOrigins` に足す |

`tauri://localhost` のような**ブラウザからは名乗れないスキーム**を足すぶんには、上の脅威（任意の Web ページが繋ぐ）は塞がったまま。`http://localhost:*` を足すときは、そのポートを開発サーバー以外に使わないこと。

**LAN 上の他端末に対する認証は無い。** 既定の `0.0.0.0` バインドは、同一 LAN の誰でもエージェントの発言を読める状態を意味する。信頼できないネットワークでは `host` を `127.0.0.1` にすること。認証の追加は [#3](https://github.com/schwarz9791/chatter-agent/issues/3)。

## 記録 — `{root}/speech.jsonl`

配信とは独立した、消さない記録。**誰も tail しない**ので、ローテートの正しさは要求されない。上限（既定 5MB）を超えたら `speech.1.jsonl` に退避するだけで、前の退避は上書きされる。

`seq` の採番は `speech.state.json` に持ち、記録の末尾からも復旧できる（両者がずれたら大きい方を採る）。
