# 発話の契約 — 記録・配信キュー・WebSocket

`chatter-agent-speak`（CLI）が発話を確定させ、`chatter-agent-server` がクライアントへ配信する。この文書は**その境界の契約**を定める。クライアント（`chatter-mascot` / `chatter-mascot-xr`）はここだけを見れば実装できる。

> 設計書 `_workspace/chatter-agent-design.md` §5 が元の一次情報だが、[#8](https://github.com/schwarz9791/chatter-agent/issues/8) で配信の形が変わったので、契約はこちらを正とする。

## 全体像

```
CLI ──┬──▶ speech.jsonl        記録。消さずに残す。誰も読まない
      │
      └──▶ speech/<seq>.json   配信キュー。1文1ファイル
                  │
                  ▼
              server ──▶ WebSocket ──▶ マスコット
                  ▲                        │
                  └────── ack ─────────────┘
```

**記録と配信を分けてある。** 1つのファイルに兼ねさせると、ローテートを跨ぐ差分読み取りが必要になり、読み手だけが際限なく複雑になる（実際に取りこぼしと二重配信を両方踏んだ）。分ければ、順序はファイル名で決まり、消費は削除で表せる。

## `SpeechRecord` — 記録・キュー・WebSocket で同一

```json
{
  "seq": 1,
  "ts": "2026-08-15T00:12:34.567Z",
  "source": "claude-code",
  "sessionId": "039211d9-…",
  "turnId": "4ccbf3aa-…",
  "messageId": "a94cd2c5-…",
  "kind": "assistant",
  "text": "ログの解析が終わりました。",
  "emotion": "happy"
}
```

| フィールド | 意味 |
|---|---|
| `seq` | 単一ワーカーがロック下で採番する 1 始まりの整数。**キューのファイル名と ack のキーを兼ねる** |
| `ts` | ISO8601 |
| `source` | `claude-code`。将来 別のプロデューサーが同じ形で書ける余地 |
| `sessionId` / `turnId` / `messageId` | 絞り込みとグルーピング。取れないときは `null` |
| `kind` | `assistant`（通常の発言）/ `prompt`（応答待ち通知）。**未知の `kind` は `assistant` として扱うこと** |
| `text` | **1文。** Markdown 除去済み |
| `emotion` | `neutral` / `happy` / `angry` / `sad` / `relaxed` / `surprised`。VRM の標準 expression 名と一対一 |

**1文1行 / 1文1ファイル / 1文1フレーム。** 3箇所で同じ形なので、変換は要らない。

## 配信キュー — `{root}/speech/`

```
{root}/speech/000000000123.json    ← ファイル名が seq（12桁ゼロ埋め）
{root}/speech/000000000124.json
```

| | |
|---|---|
| 書く | CLI（ロック下）。**tmp + rename** で置くので、server が書きかけを読むことはない |
| 読む | server が 50ms ごとに `readdir`。ファイル名から `seq` を読んで昇順に配信する |
| 消す | **上限超過は CLI**（書いた直後に切る）。**ack を受けたぶんと起動時の掃除は server** |

ファイル監視は使わない。単一ファイルの監視でローテートの取りこぼしを実測で踏んでおり、`readdir` の方が経路として単純で確実。キューは高々数百件なので、20回/秒でも誤差。

**サーバーは同時に1台だけ動く。** bind の前に `{root}/server.lock` を取り、2台目は起動に失敗する。配信キューはこのルート直下に1つしかないため、2台が同時に読み書きすると起動時の掃除や ack の削除が競合する。

## WebSocket

`ws://<host>:<port>`。既定は `0.0.0.0:8570`。テキストフレームのみ。

### サーバー → クライアント

`SpeechRecord` の JSON を1行1フレームで送る。**それ以外は送らない。**

- 接続すると、**配信済みでまだ ack していない発話**が届く（`?since=` は廃止した）。まだ配信していない分（server がまだ poll していない、または未読の entry）は含まれない
- ★ **接続の前に message ハンドラを張ること。** 接続直後の追いつきは同期で流れるので、`open` を待ってから張ると取りこぼす
- 配信が詰まる（クライアントが遅い）と、**フレームを捨てるのではなく接続を切る**（1013）。繋ぎっぱなしで1文だけ欠けるより、切って繋ぎ直させる方が事故に気づける

### クライアント → サーバー

**ack だけ。**

```json
{ "type": "spoken", "seq": 42 }
```

**累積 ack**（「seq 42 まで喋り終えた」）。1つ落ちても次で自己修復する。サーバーは `seq <= 42` のキューを消す。

`type` が `"spoken"` でない、`seq` が**非負の安全整数**でない、JSON として読めない ── これらは**メッセージとしては届いたが黙って捨てられる**（接続は切れない）。

これとは別に、**フレームそのものが 4KB を超えると黙って捨てられるのではなく、接続が 1009 で切られる。** 上の「黙って捨てられる」は正常なサイズの読めないメッセージの話で、上限超過は message イベント自体が発火せず接続断に直結する、別の失敗モード。この上限は受信専用で、サーバーからの送信（`SpeechRecord` の配信）には効かない。

## ack はフロー制御であって、耐久性の保証ではない

TTS + 再生は生成よりずっと遅い。Claude Code は 2 秒で 20 文吐くが、マスコットは 60 秒かけて喋る。**キューは実質バッファで、ack は「1文喋り終わった、次をくれ」という credit。**

この読み方から、次の3つが同じ原則で説明できる。

| | |
|---|---|
| **サーバーは起動時に、古い entry だけを捨てる** | 全消しにはしない（起動直前に書かれた entry まで巻き添えにすると、配信中メッセージの前半だけを消してしまう）。落ちている間に書かれた分だけを時間で判定して捨てる。10 秒切れて復帰したマスコットに 10 秒前の発話を今さら読ませたくない |
| **上限を超えたら古い方から捨てる（CLI が切る）** | クライアントが繋がっていなければ ack は来ない。サーバーが落ちていても ack は来ないので、歯止めをかけられるのは書き手（CLI）だけ。時間ベースの GC を足すより、上限で溢れさせる方が判断基準が1本で済む |
| **複数クライアントでは、どれか1つの ack で消してよい** | 内容は既にソケットへ配信済みで、ファイルはキュー entry でしかない |

## クライアント側の責務

1. **`seq` で重複排除すること。** 再接続すると未 ack 分が再送される。同じ `seq` を2度受け取ったら後を捨てる
2. **喋り終えたら ack すること。** ack しないとキューが上限まで溜まり、古い方から捨てられる
3. **`seq` の飛びは欠落。** 上限超過、またはサーバーの再起動（起動時に古い entry を捨てる）で起きうる。埋める手段は無いので、そのまま進む
4. **未知の `kind` は `assistant` として扱う**
5. **切断されたら繋ぎ直すこと。** バックプレッシャによる切断（1013）も含め、繋ぎ直せば未 ack 分が接続直後の追いつきで再送される

## セキュリティ

**`Origin` ヘッダを持つ接続は、`allowedOrigins` に載っていなければ拒否する。** WebSocket は CORS の対象外なので、これが無いとユーザーが開いた任意の Web ページが `new WebSocket("ws://127.0.0.1:8570")` で会話を読み、ack を投げてマスコットを黙らせられる。`host` を `127.0.0.1` に絞っても塞がらない。

`allowedOrigins` の既定は `[]`（＝ `Origin` 付きの接続は全拒否）。**完全一致のみで、前方一致やワイルドカードは無い。** Electron の `chatter-mascot`（renderer）や Unity の WebGL ビルドは `Origin` を送るクライアントなので、繋ぐときは実際のオリジンを設定に足す。

Unity（WebGL 以外）/ ネイティブクライアントは `Origin` を送らないので、`allowedOrigins` の中身に関わらず影響しない。

**LAN 上の他端末に対する認証は無い。** 既定の `0.0.0.0` バインドは、同一 LAN の誰でもエージェントの発言を読める状態を意味する。信頼できないネットワークでは `host` を `127.0.0.1` にすること。認証の追加は [#3](https://github.com/schwarz9791/chatter-agent/issues/3)。

## 記録 — `{root}/speech.jsonl`

配信とは独立した、消さない記録。**誰も tail しない**ので、ローテートの正しさは要求されない。上限（既定 5MB）を超えたら `speech.1.jsonl` に退避するだけで、前の退避は上書きされる。

`seq` の採番は `speech.state.json` に持ち、記録の末尾からも復旧できる（両者がずれたら大きい方を採る）。
